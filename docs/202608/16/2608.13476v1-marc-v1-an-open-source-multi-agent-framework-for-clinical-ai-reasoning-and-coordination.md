## 摘要
我们提出了多智能体推理与协调（MARC）框架，这是一个开源框架，用确定性的多智能体编排取代了单体式LLM提示，用于临床推理。MARC协调角色专门化的智能体，分别负责提取、推理、答案生成和评估，具有显式的上下文传递和可追溯的中间输出，实现了分阶段的失败归因。我们还引入了一个分解器模块，该模块从自然语言描述生成任务特定的智能体提示，消除了手动提示工程。该框架支持基于API和本地CPU兼容的部署，并且完全通过YAML进行配置，无需修改代码。MARC设计为模型无关、可解释，并且可供没有编程专业知识的临床领域专家使用。完整框架可在 https://github.com/Penn-RAIL/MARC-v1 获取。

## Abstract
We present Multi-Agent Reasoning and Coordination (MARC), an open-source framework that replaces monolithic LLM prompting with deterministic multi-agent orchestration for clinical reasoning. MARC coordinates role-specialized agents for extraction, reasoning, answer generation, and evaluation, with explicit context passing and traceable intermediate outputs, enabling stage-wise failure attribution. We additionally introduce a Decomposer module that generates task-specific agent prompts from a plain-language description, eliminating manual prompt engineering. The framework supports both API-based and local CPU-compatible deployments and is entirely configurable via YAML, without code modifications. MARC is designed to be model-agnostic, interpretable, and accessible to clinical domain experts without programming expertise. The full framework is available at https://github.com/Penn-RAIL/MARC-v1.

## 1. 核心问题与研究动机

### 背景
- 大型语言模型（LLM）在医学领域已广泛用于报告生成、临床问答、影像解读等任务，如 GPT-5、Med-PaLM 2、MedGemma 等模型在多项医学基准上表现优异。
- 放射学中，许多实际工作流（如结构化报告生成、随访建议提取等）不仅需要单一推理步骤，更依赖多信息源整合与多步推理。

### 核心问题
- **大多数部署系统仍然依赖单体式提示（monolithic prompting）**：单个 LLM 实例在一个提示内同时完成提取、推理、验证和动作生成。
- 这种"一刀切"的模式带来两大弊端：
  1. **可解释性差**：错误产生的环节（信息提取遗漏、推理缺陷、指令遵循失败、格式错误）被封装在一次不透明的响应中，无法定位失败根源；
  2. **模型潜力难以充分发挥**：缺乏中间步骤的上下文结构，限制了模型的推理能力。

### 整体含义
- 本文将**多智能体编排（multi-agent orchestration）**思想引入临床推理，提出 MARC 框架，把临床认知任务拆解为由角色专门化智能体执行的确定性流水线，以实现**透明、可追溯、可配置且可部署于临床环境**的 AI 系统。

## 2. 方法论

### 2.1 总体架构思想
- MARC 是一个基于 Python 的领域通用多智能体系统，采用 **Level 2 自主性（结构化工作流设计模式）**：多个专门化智能体按照**预定义的顺序**执行任务，智能体之间通过**显式上下文传递**衔接。
- 与固定流水线（如 RadFabric）不同，MARC 通过 YAML 配置文件定义智能体序列、模型分配和知识增强，**无需修改代码**即可重构流水线。

### 2.2 多智能体设计（Agents）
- 每个智能体封装三层要素：**语言模型 + 任务专属提示词 + 可选的检索增强生成（RAG）模块**。
- 智能体通过 `config/agents.yaml` 以声明方式定义，每个智能体包含四个参数：
  - 智能体名称
  - 模型标识符
  - 提示词模板文件路径
  - 可选的 RAG 上下文文件路径
- 用户可独立修改任一智能体的模型、提示词或知识源，配置与代码完全解耦。

### 2.3 Decomposer 模块（关键创新）
- **功能**：给定一个自然语言任务描述，Decomposer 利用 **MedGemma 4B** 在**单个对话回合**内完成任务理解，将任务自动拆解为**三个子任务**，并生成每个智能体的角色专用提示词模板。
- **输出**：结构化的 JSON 规范，包含智能体名称、角色和完整提示模板。
- **验证机制**：生成提示需通过一组结构性约束校验（变量绑定格式、VERDICT 格式约定、输出长度限制），通过后才写入磁盘并加载到 MARC 流水线中。
- **意义**：实现了**任务自适应的流水线自动构建**，消除了人工提示工程。

### 2.4 提示策略
- 所有智能体以**零样本（zero-shot）**、**温度 = 0** 运行，保证完全确定性和可复现性。
- 每个提示模板由四部分构成：
  1. **角色定义**：确立智能体的临床身份与职责范围；
  2. **任务指令**：明确要提取、分析或生成的内容；
  3. **输出约束**：定义格式、长度与有效答复标签；
  4. **运行时变量**：在推理时注入（`{input}`、`{previous_agent_output}`）。

### 2.5 智能体专门化（默认流水线：3 个智能体）
| 阶段 | 智能体 | 职责 |
|------|--------|------|
| Agent 1 | 信息提取器 | 接收原始输入，提取 2-4 条任务相关证据要点，**明确禁止**得出结论或回答问题 |
| Agent 2 | 分类与分析器 | 接收原始输入 + Agent 1 证据，进行结构化多步推理，评估各选项，以标准 VERDICT 行结束 |
| Agent 3 | 推荐生成器 | 接收 Agent 2 完整输出，**只定位并原样返回 VERDICT 行**，不加任何解释或改写 |

### 2.6 智能体协作与上下文传递（算法流程）
- 执行顺序为严格串行：
  1. Agent 1 接收**原始输入**（无任何先前上下文）→ 输出证据要点；
  2. Agent 2 接收**原始输入 + Agent 1 完整输出** → 输出推理过程与 VERDICT 标签；
  3. Agent 3 接收**原始输入 + Agent 2 完整输出**（隐式包含 Agent 1 的分析）→ 输出干净的最终答案。
- 每个阶段的中间输出均被记录（logging），使错误的**阶段级归因**事后可查。
- 采用标准化的 VERDICT 行（如 `VERDICT = <label>` 或 `FINAL = yes/no/maybe`），使最终预测无需启发式解析即可获得。

### 2.7 部署模式
- **模式 A：API 部署**——使用 Google Gemini 模型（gemini-2.0-flash、gemini-1.5-flash），通过 Google AI Studio，仅需配置 `.env` 中的 API 密钥。
- **模式 B：本地部署**——使用 Ollama 实现 CPU 兼容推理，适合不允许数据外传的医疗环境。
- 两种模式的配置方式完全一致（仅模型标识符不同），已在 MedGemma 4B（Ollama）和 Gemini 系列上测试。

## 6. 主要结论与发现

1. **分离比整合更可解释**：将提取、推理、答案生成拆为专门智能体后，每个中间步骤可被单独审查，支持**阶段级失败归因**——这对临床场景中的人工复核、调试和信任建立具有实际意义。
2. **编排应为可配置层而非固定实现**：通过 YAML 外部化智能体定义，临床专家无需编程即可修改工作流、替换模型、注入领域知识。
3. **Decomposer 可消除提示工程瓶颈**：从自然语言任务描述直接生成完整可用流水线，大幅降低非程序员使用门槛，支持跨任务的快速部署。
4. **本地部署是可行的临床要求**：CPU 兼容推理使受数据管控的机构也能使用多智能体框架。
5. **模型无关性保证未来兼容**：不同流水线阶段可分配不同模型族，适应成本、延迟、隐私、领域专长等综合优化需求。
6. **多智能体能否真实提升性能仍需实证验证**——作者明确呼吁未来开展广泛基准测试。

## 7. 优点

- **设计目标清晰且直击临床痛点**：针对临床 AI 最受关注的三个问题——可解释性、失败定位、非开发者的可交互性，逐一给出针对性架构解决方案。
- **声明式配置高度工程化**：将编排逻辑、模型选择、提示设计和执行代码彻底解耦，符合软件工程可维护性最佳实践，降低复现成本。
- **Decomposer 的创新性**：用轻量模型（MedGemma 4B）实现从任务描述到多智能体流水线的自动化构建，是"提示工程自动化"方向的有价值尝试。
- **双通道部署满足多类机构需求**：同时支持 API 和本地 CPU 推理，兼顾性能与隐私合规，考虑了实际医疗部署约束。
- **标准化 VERDICT 行与显式变量绑定**：通过简单的结构化约定，保证了智能体间信息传递的确定性，避免幻觉式上下文，且最终输出提取零解析成本。
- **确定性保证**：温度=0 + 零样本策略保证了同输入的输出可复现，这是医学应用中的重要设计要求。

## 8. 不足与局限

### 实验与验证层面
- **完全缺乏实证基准**：未对 PubMedQA、MedQA 等任何基准报告准确率，无法判定多智能体编排是否确实优于单体提示。
- **无性能指标**：缺少延迟、成本、吞吐等部署参数，无法评估"本地 CPU 推理"的实际可行性。
- **无消融与对照**：无法分离各智能体的独立贡献。

### 系统设计层面（作者自述 + 客观分析）
- **仅支持顺序执行**：默认流水线是严格的线性依赖，可能不适合需要并行处理、动态路由、迭代修正的任务结构。
- **三智能体架构相对固定**：虽支持通过配置扩展数量（如放射学用例为 5 个），但**缺少可变深度流水线**、分歧消解机制、人工介入（human-in-the-loop）可选环节。
- **Decomposer 的泛化性待检验**：仅用 MedGemma 4B 在单轮对话中生成提示，对于复杂任务的拆解质量、生成提示在未见任务上的鲁棒性，目前未被系统测试。
- **RAG 功能停留在"可选"层面**：框架接口支持知识库注入，但没有实验展示 RAG 引入对推理质量的影响。

### 偏差与应用风险
- **验证场景过于狭窄**：仅覆盖放射学报告与医学问答，未涉及多模态输入、长文档、时序数据或其他专科场景。
- **缺乏安全验证**：未讨论幻觉病例在流水线中的传播方式（提取错误会否被推理智能体放大？），也未提供错误严重性分级策略。
- **缺乏临床用户体验研究**：虽声称"面向无编程经验的临床专家"，但未提供临床用户的使用反馈、学习成本或可接受度数据。
